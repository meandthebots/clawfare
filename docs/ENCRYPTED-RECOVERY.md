# Encrypted SQLite backup and offline recovery

Clawfare includes **local, opt-in encrypted SQLite backup and offline
restore-to-new-path** commands for sensitive travel records. There is no
cloud upload, hosted D1 access, live provider request or booking operation.

## Commands

Create a secret file without putting the secret on the CLI command line.
For example, on a POSIX machine:

```sh
umask 077
# Supply a unique, high-entropy passphrase using a trusted local method.
# Put its UTF-8 bytes into ~/private/clawfare-backup-passphrase (mode 0600).
chmod 600 ~/private/clawfare-backup-passphrase
clawfare --db ~/.clawfare/data.db db backup \
  --out ~/private/clawfare-2026-11-17.clwdb \
  --passphrase-file ~/private/clawfare-backup-passphrase
```

The destination directory must **already exist** and support POSIX private
permissions and hard links. Backups never overwrite existing files. Use a
unique archive name for every backup. A live SQLite writer may keep its WAL
file open: Clawfare uses SQLite `VACUUM INTO` to capture a consistent
snapshot including **committed WAL transactions**.

Restore a verified archive into a **new**, absent SQLite pathname, without
modifying the original database, its journals, or the archive:

```sh
clawfare db restore \
  --from ~/private/clawfare-2026-11-17.clwdb \
  --into ~/private/clawfare-recovery-check.sqlite \
  --passphrase-file ~/private/clawfare-backup-passphrase
sqlite3 ~/private/clawfare-recovery-check.sqlite 'PRAGMA integrity_check;'
sqlite3 ~/private/clawfare-recovery-check.sqlite 'PRAGMA user_version;'
```

Restore refuses existing target databases, symlinks, and even pre-existing
`-wal`, `-shm`, or `-journal` sidecars. It never initializes the global
Clawfare connection or automatically migrates the restored database.
Inspect investigations, recent prices, source status and token age before
using a recovered database. Only after stopping all writers should an
operator consider replacing the active DB, following
[SCHEMA-MIGRATION.md](SCHEMA-MIGRATION.md). Recovery is not activation.

## Archive format, privacy and limitations

Version `CLWDB001` consists of an eight-byte magic/version identifier,
16 random salt bytes, 12 random nonce bytes, and an AES-256-GCM encrypted
SQLite file including a 128-bit authentication tag. Key derivation uses
PBKDF2-HMAC-SHA256, **250,000 iterations**, and a 256-bit derived key.
The full header is authenticated as additional data. Unknown versions,
incorrect secrets, and modified ciphertext cause restore to fail **before**
an output database is published. This is a deliberately small, fixed
format, not a general-purpose archive or key-management system.

Use a **unique high-entropy passphrase** of at least 16 characters,
preferably generated by a password manager. The passphrase file must be a
regular, non-symlink POSIX file with no permissions for group or others;
one terminal newline is removed. Do not commit the file, log the secret,
put it into shell history, or distribute the archive together with its key.
A lost passphrase cannot be recovered by Clawfare. Protect and test an
off-site copy of both the archive and the separately secured recovery key.

Plaintext SQLite is temporarily written into a private **0700** directory
during backup/decryption and deleted after success or failure. Individual
files are set to **0600**, and archive/recovery publication uses exclusive
hard links so that existing destinations are never overwritten.
**Deletion does not securely erase disk blocks, SSD snapshots, backups, or
swap**, and neither the source SQLite DB, its WAL, nor old unencrypted
migration snapshots become encrypted. Use disk encryption for the host.
No Windows ACL implementation is provided; non-POSIX filesystems fail
closed instead of silently weakening permissions.

The encrypted archive contains **only the SQLite database**. Separate
budget, attempt, price-alert and audit journals, plus external disk-cache
files, are NOT included. Full disaster recovery also requires separately
secured copies of those files, consistent with the financial budget ledger.
Historical token replay data in the restored DB must not be considered
current offers. Archive retention, key rotation and off-host recovery
automation remain open under issue #25.

## Verification

Synthetic unit/integration tests exercise: active WAL containing committed
records; encrypted round-trip into a standalone DB; integrity checks and
owner-only permissions; incorrect passphrase and ciphertext tampering;
refusal to overwrite existing archives, DBs or WAL sidecars; safe handling
of symlinks and permissive passphrase files; and no leftover temporary
staging directories. No real credentials or travel plans are used.
